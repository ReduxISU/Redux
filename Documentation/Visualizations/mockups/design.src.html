Clause Graph

approved

Variables on the left, clauses on the right. A solid edge means the clause contains x, and a dashed edge means it contains ¬x. Once a variable is assigned, the edges it makes true turn green and the others fade, so a clause is satisfied when at least one of its edges is green. This is the same Bipartite graph type the set problems use.

One node per literal, grouped into one cluster per clause. Edges join a literal to its complement in another clause, so a satisfying assignment shows up as one green literal in every cluster. Hover a literal, either in the graph or in the formula, to trace that variable everywhere it appears.

Input contract

The problem supplies clauses and nothing visual. The shared Grouped graph base derives the clusters, the complement edges and the colors, so SAT and 3-SAT get identical pictures from the same code.

// What SAT / 3-SAT must hand over (required)
clauses:     int[][]         // [[-1, 2, 3], [-1, -2, 4], ...]  sign = polarity
variables?:  string[]        // display names, default x1..xn

// Solved view
assignment:  bool[]          // index = variable

// Steps view, one entry per frame
frames: { assignment, tried?: int, rejectedClause?: int, caption }[]

What the base sends to either frontend:

{
  "type": "GroupedGraph",
  "layout": "ring-of-groups",
  "groups": [{ "id": "C1", "label": "C1", "state": "Satisfied" }],
  "nodes":  [{ "id": "C1.0", "label": "¬x1", "group": "C1",
               "key": "x1", "state": "Solution", "witness": true }],
  "edges":  [{ "source": "C1.0", "target": "C6.0",
               "kind": "complement" }]
}

key links nodes across groups, and hover-tracing uses it here. Groups line up with what the SAT3 → Clique reduction already emits: its ClauseHighlight gadget names the nodes in each clause. So the reduction's target picture could use this same layout instead of a force layout.

For review

  1. Edges. Complement edges are shown by default. The within-clause edges (dashed) make this exactly the 3-SAT → Independent Set graph. Should they be on by default, or stay a toggle?
  2. Scale. The ring layout reads well up to about 12 clauses. Past that, should it switch to a grid of clusters, or should the frontend refuse and fall back to the plain clause list?
  3. "False" state. The current vocabulary has no state for an assigned-but-false literal. This mockup draws it as a muted node. Add it as a real state, or reuse Background?

Automaton

approved

States laid out left to right in the order the machine reaches them from the start state. The start state gets an incoming arrow and accept states get a double ring. Transitions between the same two states share one arrow with a combined label. The input tape underneath shows what has been read.

Redux format: ((States, Alphabet, Transitions, Start, Accept), input). NFA transitions may use ε.

  "type": "Automaton",
  "layout": "layered-from-start",
  "nodes": [{ "id": "2", "initial": false, "accept": true,
              "state": "Solution" }],
  "edges": [{ "source": "2", "target": "3", "labels": ["b"],
              "epsilon": false, "state": "ElementHighlight" }],
  "tape":  { "symbols": ["a","b","a","a","b"], "read": 2 }

Edge labels stay strings and are never fed to a number scale. Today's GUI graph renderer runs d3.scaleLinear over the weight field, which breaks on labels like "a,b".

Decisions

  1. NFA steps (decided). All branches at once is the default. "One path" follows a single run, picked from a dropdown that lists each path with its outcome.
  2. Missing DFA transitions (decided). They lead to a separate, isolated Garbage state drawn in red. A run that falls in stays there and is rejected.
  3. TikZ (decided). TikZ comes out of the visualizations once every one of them has been ported to D3.

Bipartite Graph

approved

Elements of U on the left, the sets of S on the right, and an edge for every membership. The certificate picks from one side and constrains the other. Set Cover and Exact Cover pick sets that must cover every element. Exact Hitting Set picks elements so that every set contains exactly one of them. The steps come from whichever solver is selected.

Solver

Chosen

Checks

    Key

    SolutionChosen by the certificate. The column marked ● PICKED is the side it chooses from
    CoveredHit by a chosen node, the required number of times
    ElementHighlightThe choice the solver is trying now
    BlockedWould double up on something already covered
    RejectedLeft uncovered, covered twice, or out of options

    Input contract

    All three problems already parse into a universe and a list of sets. Today their visualizations re-send that nested list, so moving to this shape changes what goes over the wire. That needs a matching frontend change.

    // What Set Cover / Exact Cover / Exact Hitting Set hand over
universe:  string[]
sets:      string[][]
k?:        int                        // Set Cover only
pick:      "sets" | "elements"        // side the certificate names
rule:      "atLeastOnce" | "exactlyOnce"

// Solved view
chosen:    string[]

// Steps view: emitted by the selected solver, not the visualization
frames: { chosen, trying?, focus?, missing?, trial?, caption }[]

    What the base sends to either frontend:

    {
  "type": "BipartiteGraph",
  "left":  { "title": "Elements", "nodes": [
             { "id": "e:4", "label": "4", "state": "Covered" }] },
  "right": { "title": "Sets", "nodes": [
             { "id": "S4", "label": "S4", "detail": "{4,5}",
               "state": "Solution" }] },
  "pickSide": "right",
  "edges": [{ "source": "e:4", "target": "S4", "state": "Solution" }]
}

    The set column is sorted by the average position of each set's elements, which cuts down on crossing edges. Set names stay in instance order (S1, S2, …), so they always match the certificate.

    Decisions

    1. Name matches the implementation. Redux's Hitting Set requires exactly one chosen element per set, so it's called Exact Hitting Set. The problem's name and definition in Redux need the same change.
    2. Steps come from the solver. Each solver emits its own frames, and the visualization only draws them. Pick Greedy or Brute Force for Set Cover to see the difference. Greedy now reports its own overshoot instead of quietly swapping in another answer.
    3. Covered and Blocked join the shared states. The ×2 badge is a count drawn on a node, not a state. See State vocabulary below.
    4. SAT factor graph. Added as a second visualization for SAT and 3-SAT, on the SAT tab.

      For review

      1. Layout. Force layout by default, and Circle by default for tours (Hamiltonian, TSP), since a tour reads best around a ring. Both are deterministic, so the same instance always looks the same. Keep that split, or let each problem choose?
      2. Missing edges. When an answer needs an edge the graph doesn't have, the edge is drawn as a red dashed line that isn't in the graph. Is that clear, or does it look like part of the instance?
      3. Color classes. Graph Coloring and Max Cut fill nodes with a group color instead of a state color. Six colorblind-safe colors are defined. Is six enough, or should more than six classes switch to numbered labels?
      4. Solvers not in Redux. Dominating Set's two real solvers have no steps here yet, and Minimum Cut's real solver (Stoer-Wagner) merges nodes between phases, which needs a "merged node" drawing. Both use a brute-force stand-in, labeled as such.
      5. Loose verifiers. Redux's Cut and Weighted Cut verifiers accept any K edges, even ones that don't separate the graph, and the Steiner Tree verifier never checks K. The mockup follows the solvers, which do require a real cut and respect K. The verifiers should match.

      Flow Network

      approved

      The source sits at the far left and the sink at the far right, with every other node placed by how many hops it is from the source. Each edge reads flow/capacity and gets thicker as it fills. Each step pushes flow along one path that still has room. When no path is left, the nodes the source can still reach form one side of the cut, and the full edges leaving that side add up to the maximum flow.

      Solver

      Path or cut

      Checks

        Key

        ElementHighlightThe path flow is being pushed along
        Full edgeFlow equals capacity. Thicker means fuller
        Backward arcRoom to take flow back, drawn when a path uses it
        S and TNodes the source can still reach, and the rest
        SolutionCut edges: full, from S to T, summing to the max flow

        Input contract

        Minimum S-T Cut already parses into a node set, capacitated directed edges, a source and a sink. Today its picture is a plain graph with the cut highlighted. This view adds the flow on each edge, so the steps can show why the cut is where it is.

        // What Minimum S-T Cut hands over
nodes:   string[]
edges:   { from, to, capacity }[]
source:  string
sink:    string

// Solved view: the S side, e.g. {1,2}
// Steps view: one frame per augmenting path, from the solver

        A step is in the problem's own terms: how much flow each edge carries and which path it was pushed along. Edmonds-Karp and Ford-Fulkerson both fit it, so either solver can drive the picture.

        For review

        1. Backward arcs. By default a backward arc only appears when a path uses it. "All backward arcs" shows every edge that has flow to give back. Keep the quiet default?
        2. Edge thickness. Edges thicken as they fill, and full edges turn solid dark. Is thickness enough, or should the flow/capacity label carry it alone?
        3. Minimum Cut (undirected). Redux's other cut problem uses Stoer-Wagner, which doesn't push flow. Draw it on the base Graph view with a two-group split instead?

        approved

        Directed graphs drawn left to right in ranks, so most edges point forward. Edges that point backward close a cycle, and they run as curves under the rows where they're easy to spot. That matters for Topological Sort and the Feedback Set problems. Shortest-path problems show each node's distance under it, filling in as Dijkstra settles nodes.

          The same idea as the base Graph, for directed edges. A problem hands over the graph, a source and target where it has them, and the shape of its answer. The base works out the ranks, finds the back edges and derives every color.

          // 1. The graph (already parsed by every one of these problems)
nodes:   string[]
edges:   { from, to, weight? }[]

          Dijkstra's frames carry the distance table and each node's predecessor. The existing SSSP and SPSP table views show distances too, so one recording could drive both the table and this graph.

          For review

          1. Back edges. Edges that point backward run as curves under the rows. Is it clear they're what makes a cycle, or should they also get their own color?
          2. Removed edges. A Feedback Arc Set answer draws its removed edges as dashed green lines, because they're the answer. Would crossed-out or faded read better, since they're being deleted?
          3. Dijkstra. Distances sit under each node, ∞ until reached, and the edges just checked are highlighted. Should the queue of nodes waiting to be settled be shown too?
          4. Kosaraju. The first pass shows finish numbers (#1, #2 …) above the nodes, and the second pass colors each component. Is that enough to follow the two passes, or should the second pass also show the reversed edges?
